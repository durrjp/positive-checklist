# Positive Checklist — Concept & Tech Stack Plan

*Last updated: 2026-08-14*

## The idea in one line

A free iOS app where you build genuine self-worth by completing goals so small they barely feel like goals — "texted the coworker I've been meaning to catch up with," "vacuumed one room" — organized under bigger life themes, made satisfying through gamification, with a guided (non-AI) chatbot that helps you figure out what small goals even fit your life.

## Core mechanics

**Big Goals → Small Tasks.** The user creates a handful of Big Goals (life areas: "Be a better friend," "Keep the house livable," "Move my body more"). Under each, they add Tiny Tasks — deliberately sized small enough to feel almost trivial. The app should actively coach users toward *smaller* tasks, not bigger ones; this is the whole differentiator from standard to-do/project-management apps.

**Completion is the reward.** Every checkbox tap should feel good on its own — a satisfying animation, a sound, a streak tick — independent of any points system. The gamification layer (below) reinforces this but shouldn't be required for the core loop to feel good.

**Categorization, not deadlines.** Unlike project management tools, there's no due-date pressure. Tasks live under their Big Goal and get completed whenever. Consider a lightweight "today" surface (a short list pulled from across goals) so the app still gives daily structure without becoming a task-anxiety machine.

## Gamification ideas

- **Streaks per Big Goal**, not just a global streak — so missing a day on "house" doesn't kill your "friendships" streak.
- **Completion animations**: confetti burst, a satisfying checkmark "pop," haptic feedback (iOS Taptic Engine) on every completion.
- **Momentum/level system** tied to consistency, not volume — e.g., a "glow" meter per Big Goal that fills with small completions and gently fades if untouched, rather than a punishing streak-reset.
- **Reflection over leaderboard.** Avoid competitive/comparison mechanics (leaderboards, social feeds) — they cut against the mental-health goal. Favor a private "look how far you've come" view: a calendar heatmap of completions, a running count of "tiny wins," maybe a periodically generated recap ("This month you did 34 tiny things for yourself").
- **Positive framing everywhere.** No red "overdue" states, no shame language. Missed days are just blank, not broken streaks — consider a "streak freeze" or soft-landing mechanic so lapses don't feel punishing.

## The chatbot (guided flow, not full AI — for v1)

- Model it as a **decision tree / structured wizard**, not open-ended chat: "Which part of life feels most neglected right now?" → branches (relationships, home, health, self-care, work) → "How much energy do you have today — low / medium / high?" → surfaces a curated bank of example tiny-tasks matched to that combination, editable before saving.
- Build the task bank as a simple JSON table you can expand over time — this is content work, not engineering, and it's where a lot of the app's "soul" will live.
- Design it so upgrading to a real LLM later is a drop-in swap: keep the wizard's *output* (a Big Goal + suggested Tiny Tasks) the same shape whether it's generated by rules or by a model, so the rest of the app doesn't care which one produced it.

## Recommended tech stack

Given: iOS first with Android kept realistic later, local-only (no backend) to start, leveraging existing React/TypeScript and NoSQL background, and a document-shaped data model (goal with embedded tasks) rather than a heavily relational one.

**Framework: React Native with Expo (managed workflow), TypeScript.**
Standard recommendation for a JS/TS developer's first mobile app. Expo removes almost all of the native-tooling pain (no need to touch Xcode project files, provisioning profiles, or CocoaPods directly for most of development) while still producing a real native app. Keeps Android available for free later since it's the same codebase.

**Local data: `react-native-mmkv`, storing data as JSON.**
The data is naturally document-shaped — a Big Goal with its Tiny Tasks embedded is one object, not a set of tables needing joins — and at the scale a personal app like this runs at (dozens of goals, maybe hundreds of tasks), a JS array filter over an in-memory JSON blob is plenty fast. MMKV is a fast, synchronous key-value store — store entities as JSON blobs (e.g. a `goals` key whose value is the full array of goal objects). TypeScript interfaces (`Goal`, `Task`, `CompletionEvent`) become the schema, since nothing enforces structure at rest. Note: MMKV is a native module, so it needs a custom dev client via EAS rather than plain Expo Go — a one-time setup step, not a blocker.

**State management: Zustand, with its MMKV-backed `persist` middleware.**
Lightweight, minimal boilerplate, and the `persist` adapter keeps the in-memory store and on-disk JSON in sync with almost no extra code.

**UI/animation:**
- `react-native-reanimated` + `react-native-gesture-handler` for smooth completion animations and swipe interactions.
- `lottie-react-native` for polished celebration animations (confetti, checkmarks) — huge free asset libraries on LottieFiles.
- `expo-haptics` for the satisfying tap feedback.
- `expo-notifications` for gentle local reminders/streak nudges (no backend required for local notifications).

**Build & App Store submission: EAS (Expo Application Services).**
EAS Build compiles the app in the cloud and can submit directly to App Store Connect (`eas submit`), so a Mac isn't strictly required for most of the process, though access to one (or a cloud Mac) is still useful for final polish/testing in Simulator. EAS has a free tier sufficient for a solo indie project's early builds.

**Cost to actually ship: Apple Developer Program is $99/year** — required for App Store submission and TestFlight beta testing, and really the only hard cost for a local-only free app.

### Why not native Swift/SwiftUI or Flutter?
Both are perfectly good choices, and Swift in particular gives the most native feel — but leveraging existing JS/TS skills over learning a new language/ecosystem first makes React Native/Expo the better fit: learning *mobile patterns* on top of a known language, instead of a language and mobile patterns simultaneously. Flutter (Dart) is a strong alternative but doesn't reuse existing JS knowledge either.

### On the eventual MongoDB goal
Worth flagging: MongoDB's own mobile embedded-sync product, **Realm / Atlas Device Sync, is now fully deprecated / end-of-life** — that was the product that would've given "local JSON auto-syncs to Atlas" out of the box. It's gone, so don't design around it. The practical path to "storing in Mongo eventually" is: stand up a small Node/Express + Mongoose API in front of MongoDB Atlas (a free M0 tier exists) and sync local JSON documents up over plain REST when ready. Because the local MMKV data is already document-shaped, the local `Goal` object and the Mongo `Goal` document can be nearly identical — a much smaller lift than migrating out of a relational schema would have been.

## Suggested build phases

1. **Bare-bones MVP (local only):** Create Big Goals, add/complete Tiny Tasks, basic completion animation + haptics. No gamification yet beyond "it feels good to tap." Get this on a phone via an EAS dev build ASAP.
2. **Gamification layer:** per-goal streaks/glow meters, calendar heatmap, recap view.
3. **Guided goal-wizard (the "chatbot"):** decision-tree flow + curated task bank.
4. **Polish for release:** onboarding, app icon/branding, empty states, accessibility pass, App Store screenshots/copy.
5. **TestFlight beta:** get a handful of real people using it before public launch — this matters a lot for a mental-health-adjacent app.
6. **Submit to App Store.**

## Learning resources (new to mobile)

- Expo's own docs are unusually good for onboarding — start at docs.expo.dev, specifically the "Get started" guide.
- Build with an EAS dev client on your own phone from day one — live reload on a real device, and native modules like MMKV work, unlike plain Expo Go.
